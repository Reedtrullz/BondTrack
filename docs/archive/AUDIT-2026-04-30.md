## Executive summary

The app has a strong dashboard skeleton and several high-value Investment Command Center concepts, but it is not production-trustworthy yet for bond-provider decisions or transaction workflows.

Highest-risk findings:

1. P0 transaction bug: BOND composer treats the visible “Bond Amount” as a provider-address memo field, so entering `10` can generate `BOND:<node>:10:0` instead of using `10 RUNE` only as the deposit amount.
2. P0/P1 financial correctness: displayed APYs are implausibly high for the provided address (`~288% weighted APY`, node rows `~275-295%`) and are derived from `current_award * CHURNS_PER_YEAR`; this should be revalidated against Midgard/network APY semantics before users rely on it.
3. P0 local/test reliability: localhost always enters mock-data mode, so local QA with the provided address shows mock positions instead of real data. This also breaks unit tests and hides live-data issues.
4. P0/P1 rewards page correctness: on dev, the same address that shows 3 live bond positions on Portfolio/Nodes shows `0.00` PnL and `Loading APY data...` on Rewards, creating a major cross-page inconsistency.
5. P0/P1 tax/export correctness: tax report FIFO and LP income calculations can silently omit or misstate historical data because they fetch only 50 actions, filter before building lots, and allocate current LP units across historical intervals.
6. P1 API/security: committed CoinAPI fallback key, open CORS proxy, unbounded quota-burning endpoint, weak validation, and dynamic API routes that ignore their path params.
7. P1 QA gates fail: lint fails, unit tests fail, and e2e tests fail. TypeScript and production build pass under Node 20.
8. P1/P2 UX completeness: Rewards contains metric-label cards with no values, notification prompt repeatedly overlays dashboard content, branding still says Heimdall/THORNode Watcher rather than BondTrack, and several empty/error states collapse upstream failure into “no positions.”

## Findings

### P0-1. BOND composer uses “Bond Amount” as provider-address memo field

Evidence:
- `src/components/dashboard/transaction-composer.tsx:79` stores the visible bond amount in `bondProviderAddress`.
- `src/components/dashboard/transaction-composer.tsx:117-122` passes it to `generateBondMemo(nodeAddress, bondProviderAddress, nodeOperatorFee)`.
- `src/components/dashboard/transaction-composer.tsx:124-130` also uses it as preview transaction amount.
- `src/lib/transactions/bond.ts:214-218` formats the second argument as provider address: `BOND:<node>:<provider>:<fee>`.

Impact:
- A user entering `10` in “Bond Amount” can create memo `BOND:<node>:10:0`.
- This is semantically wrong and could cause failed or unsafe bond transactions.

Fix:
- Split state into `bondAmount` and optional `providerAddress`.
- Default memo should be `BOND:<node>` for normal top-up.
- Treat provider address and operator fee as advanced fields.
- Add unit/e2e tests asserting amount `10` does not appear in the provider-address memo slot.

### P0-2. UNBOND memo uses human amount, not documented 1e8 base units, and transaction coin amount is coupled to unbond request

Evidence:
- `src/lib/transactions/bond.ts:221-222` returns `UNBOND:${nodeAddress}:${amount}`.
- `src/components/dashboard/transaction-composer.tsx:121` passes the user-entered value directly.
- `src/lib/transactions/bond.ts:70-85`, `117-125`, and `154-162` also use the same amount as wallet transaction amount.
- `src/lib/transactions/AGENTS.md` documents `UNBOND:<node_address>:<amount_in_1e8>`.

Impact:
- Entering `10` RUNE creates `UNBOND:<node>:10`, not `UNBOND:<node>:1000000000`.
- The requested unbond amount is coupled to deposited coin amount across wallets.

Fix:
- Parse decimal amounts strictly to `BigInt` 1e8 base units.
- Generate unbond memo with base units.
- Validate requested unbond amount against the user’s actual bond.
- Confirm correct wallet-specific THORChain MsgDeposit behavior and test per adapter.

### P0-3. Displayed APY is likely materially overstated

Evidence:
- `src/lib/types/node.ts:57` calculates `netAPY` from `calculateAPY(bondSharePercent, node.current_award, operatorFee, provider.bond)`.
- `src/lib/utils/calculations.ts:24-32` converts `currentAward`, allocates provider share, multiplies by `NETWORK.CHURNS_PER_YEAR`, then divides by bond.
- Dev browser for the test address displayed weighted APY `288.18%` and node APYs around `275-295%`.
- A live sanity check from the audit subtask found Midgard network `bondingAPY` around `0.6334` decimal, about `63.34%`, far below displayed user APYs.

Impact:
- Annual earnings, daily earnings, fee leakage, reward projections, optimizer suggestions, and user decisions can all be inflated.

Fix:
- Verify THORNode `current_award` semantics before annualizing.
- Prefer Midgard historical bonding earnings / total bond / elapsed days for baseline APY.
- If node-specific APY is estimated, label it clearly and bound it against protocol-wide historical context.
- Add fixtures using this address shape and assert APY stays within a defensible range.

### P0-4. Localhost always uses mock data, invalidating local QA with real addresses

Evidence:
- `src/lib/mock-data.ts:80-86` returns mock mode for `localhost` and `127.0.0.1`.
- `src/lib/hooks/use-rune-price.ts:11-14`, `use-bond-positions.ts`, and `use-earnings.ts` skip SWR calls when mock mode is true.
- Local browser test with the provided address showed two mock positions (`thor1qlfaaz...`, `thor1abc...`) and weighted APY `1396.73%`, not the live address data.

Impact:
- Local QA can pass with fake data while live data is broken.
- Unit tests expecting mocked APIs fail because hooks never call the mocked fetchers.

Fix:
- Replace hostname-based mock mode with explicit `NEXT_PUBLIC_USE_MOCK_DATA=true`.
- Disable mock mode in `NODE_ENV=test` by default.
- Add a visible “Mock data” badge if mock data is ever shown.

### P0-5. Tax export can silently misstate bond FIFO and LP income

Evidence:
- `src/lib/utils/tax-export.ts:94` fetches only 50 bond/unbond/leave actions.
- `src/lib/utils/tax-export.ts:96-99` filters actions to the report range before building FIFO lots.
- `src/lib/utils/tax-export.ts:138-150` consumes only those in-range lots for unbond cost basis.
- `src/lib/utils/tax-export.ts:173-199` uses current member LP units for historical earning allocation.
- `src/lib/utils/tax-export.ts:222-230` can use historical total pool units, but not historical user units.
- `src/lib/utils/tax-export.ts:258-259` treats `endDate` as midnight at the start of the end date.

Impact:
- Unbonds inside the report can get zero/understated cost basis if original bonds were before the report start date.
- LP income can be assigned to periods before the user held the LP position.
- End-date events after midnight are excluded.

Fix:
- Build FIFO lots from all bond actions up to `endDate`; only emit taxable events inside the selected range.
- Paginate actions or return an explicit incomplete-report warning/error.
- Use historical user liquidity units per interval, or mark LP tax rows as estimated/incomplete.
- Treat end date as inclusive calendar day, or use `< nextDayStart`.

### P1-2. API routes named with dynamic segments ignore path params

Evidence:
- `src/app/api/address/[address]/route.ts:4-10` reads only `searchParams.get('address')`.
- `src/app/api/pools/[pool]/route.ts:4-10` reads only `searchParams.get('pool')`.
- Browser/curl verification: `/api/address/thor158q...2dy2` returns 400 `{ error: "Address parameter is required" }` locally/dev.

Impact:
- The REST contract implied by the route path is broken.
- Production currently returned a 404 for this route shape, showing deployment/API drift.

Fix:
- Use Next route params: `{ params }: { params: Promise<{ address: string }> }` and same for pool.
- Or rename routes to query-only endpoints.
- Add e2e/API tests for both direct path and query usage if both are supported.

### P1-3. Open CORS proxy and public relay behavior

Evidence:
- `src/app/api/midgard/[...path]/route.ts:45-50` and `65-70` set `Access-Control-Allow-Origin: *` and allow `GET, POST, OPTIONS`.
- `src/app/api/thorchain/[...path]/route.ts:30-35` and `48-53` do the same.
- Both are arbitrary catch-all proxy routes.

Impact:
- Any third-party web page can use the deployment as a public browser-callable Midgard/THORNode relay.
- Even with public data, this is an availability and rate-limit abuse risk.

Fix:
- Restrict CORS to production/staging origins.
- Allow only methods actually implemented, normally `GET, OPTIONS`.
- Add endpoint allowlists and rate limiting.
- Cache safe public responses.

### P1-4. CoinAPI key fallback and quota-burning endpoint

Evidence:
- `src/lib/api/coinapi.ts:1` contains a committed fallback key.
- `src/lib/api/coinapi.ts:20-24` sends the key in request headers.
- `src/lib/api/coinapi.ts:66-73` builds historical range URLs directly from inputs.
- API route accepts arbitrary date ranges without auth/rate-limit/max range.

Impact:
- The key should be considered exposed and rotated.
- Public endpoints can burn quota.

Fix:
- Remove fallback key; require server-only env var and fail closed if absent.
- Rotate the key.
- Enforce date validation, max range, cache, and rate limiting.
